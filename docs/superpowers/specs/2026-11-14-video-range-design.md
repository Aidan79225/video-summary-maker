# YouTube 影片區間（`add_video --start / --end`）— 設計

接續 `2026-10-31-youtube-videos-design.md`（第二部分：多人說話者）。決定編號接著那份的 #29。

## 動機與目標

第一次用真的影片跑多人模式（2026-11-14，`ReXUCiDCbl8`），在聲音區分之後、呼叫任何模型之前被擋下來：`--speakers 14` 找到 7 位主要發言者、7 個其他聲音，共 14 個聲音，超過發佈上限 12 個。操作者的影片是一場**辯論**，前面和後面各有一些「其他人的採訪」，那些片段不重要——超出上限的聲音幾乎都來自那裡。

目標：

1. `add_video` 可以指定 `--start`、`--end`，只處理影片裡**一段連續的區間**（辯論本體）。
2. 區間外的聲音不會被聲音區分看到，所以不會被算進人數、不會占用 12 個聲音的上限，也不會花語音辨識的時間。
3. 發佈的每一個時間、每一個 `&t=` 連結都還是**原影片的**時間；讀者點進去聽到的就是那一句。
4. 說話者歸屬的保證一個字都不放寬：區間只改變「GPU 聽哪一段音訊」，其餘（對齊、核對、門檻、Pi 的驗證）完全沿用。

## 非目標

- **不自動找出「辯論本體」。** 區間由操作者給。
- **不支援一支影片多段區間**（也不把多段併成一篇或拆成多篇）。一支影片一篇文章（`yt-<id>`），一篇一個區間。
- **不放寬 12 個聲音的上限**，也不改 8 位主要發言者的上限。那是另一個決定，要有真實影片的資料、也要操作者同意才動（上限是 Pi 驗證器的大小界線，不是量出來的歸屬安全值；見設計文件 #24）。有了區間之後，這個操作者的影片不需要它。
- **不從 YouTube 只下載區間**（yt-dlp `--download-sections`）：邊界落在關鍵影格上、不精準，而且要重新編碼；時間偏移會變得不確定。GPU 一律下載整段音訊再用 ffmpeg 切。
- **單人模式（`--speakers 1`）不支援區間**，見 #34。

## 做法（考慮過的三種）

| | 做法 | 取捨 |
|---|---|---|
| A（採用） | GPU 下載整段音訊 → ffmpeg 切出區間 → 聲音區分與語音辨識只吃那一段 → 所有時間加回區間起點 | 音訊多下載一些（影片的音訊只有幾十 MB，不是問題）；區間外的聲音完全不進來；改動集中在「聽」這一步，之後的對齊、核對一律不變 |
| B | 整段都做完，再把區間外的結果丟掉 | 白花整支影片的聲音區分與辨識時間；而且聲音區分是看整段音訊聚類的，區間外的人會影響區間內的分法，12 個聲音的問題也沒解決（上限檢查是在對齊之後） |
| C | 用 yt-dlp 只下載區間 | 省頻寬，但邊界不精準、容易失敗，時間偏移要靠猜；Windows 與 Docker 上 `--download-sections` 還要 ffmpeg 重新編碼 |

選 A 是我（Claude）的決定：操作者請我直接做，沒有走確認。理由是它最小：新增的只有「切」與「加回起點」兩件事。

## 決策

| # | 決定 | 理由 |
|---|---|---|
| 30 | **一支影片一個連續區間。** `--start`、`--end` 可以只給其中一個：只給 `--start`＝從那裡到結尾；只給 `--end`＝從頭到那裡。格式與 `diarize_check` 一致：秒數、`mm:ss`、`h:mm:ss`（分與秒不超過 59、不收負數與空白以外的雜字）。GPU 的請求欄位是 `range_start`、`range_end`（秒，浮點數；省略＝沒有那一端） | 操作者的情境就是「中間一段是重點，前後是別人的採訪」。一個起點加一個終點最容易說清楚、也最不容易打錯 |
| 31 | **先切再做。** `BuildDeckUseCase` 在下載完音訊之後，用音訊切割器（新的 port `AudioCutter`，ffmpeg 實作：`-ss`、`-t`、單聲道、16 kHz、WAV）切出區間，聲音區分與語音辨識都只吃切出來的檔案，`SpeakerTurn` 與每個 `Word` 的時間在**存檔與對齊之前**加上區間起點。切出來的檔案放在同一個暫存資料夾，工作結束時跟音訊一起清掉。`diarize_check --start/--end` 改成用同一個切割器（不再自己留一份 `ffmpeg_cut`） | 見上面的 A。切割器是 port：use case 不知道 ffmpeg，測試用假的 |
| 32 | **時間軸永遠是原影片的。** 區間不改變任何發佈出去的時間的意思：重點的 `start`、頁的 `timestamp`、說話者的 `first_seen`／`last_seen`／`samples`、逐字稿每一行的時間、截圖與影片片段的時間、`&t=` 連結、`label_video --audit` 的連結，都是原影片的秒數。截圖與影片片段本來就是依頁的 `timestamp` 從原影片抓的，不必動 | 讀者要點連結去原影片驗證；一個偏移了十分鐘的連結，是另一種「安錯人」 |
| 33 | **區間的驗證與夾住。** `start ≥ 0`、`end > start`、數字必須有限（否則 `ValueError`／API 422／指令錯誤）。影片實際長度要下載之後才知道：`start ≥ 長度` → 工作失敗並說明長度；`end > 長度` → 夾成長度（結果回報的是夾過的實際區間）；`start` 是 0 而 `end` ≥ 長度 → 等於沒有區間（不寫「只處理…」、不回報區間）。切出來的音訊少於 5 秒也算失敗（`AudioCutFailed`）。Pi 在預檢時讀得到影片長度：`start ≥ 長度` 在登記之前就拒絕；`end > 長度` 只提醒、照送（GPU 會夾） | 打錯的終點（例如把 `58:00` 打成 `5:80`）會被格式檢查擋下；超過結尾的終點意思很明確（到結尾），夾起來比失敗友善，而且結果與註記會說實際處理了哪一段 |
| 34 | **只有多人模式。** 單人路徑用整支影片的字幕（cues），沒辦法切。所以：`--speakers 1` 加區間 → 指令錯誤（說明原因）；GPU 的 `POST /jobs` 對 `speaker_mode` 是 `single`、或是分類／追問工作帶了區間 → 422；`BuildDeckUseCase.execute(speaker_mode="single", time_range=…)` → `ValueError`。**絕不默默忽略區間**——那會把整支影片發佈出去，而操作者以為只有那一段 | 默默忽略是這個功能最糟的失敗方式 |
| 35 | **存檔指紋。** 區間算進聲音區分與語音辨識的指紋，**只在有區間時才加**：沒有區間的指紋與加入區間之前逐位元組相同（舊存檔照常沿用，議會與單人完全不受影響）。摘要的指紋本來就含每一段話的時間，所以換了區間會自然重做。同一支影片換區間，兩個耗時的階段都會重做，不會拿別段的結果冒充 | 設計文件 #28 的原則：輸入一變，舊存檔就不能被沿用 |
| 36 | **GPU 能力旗標 `video_range`。** `GET /capabilities` 多回 `video_range: true`（舊的 GPU 沒有這個鍵）。Pi 要送區間之前先檢查，不是 `true` 就在登記之前停下來，請操作者先更新 GPU 主機。`speaker_contract` 維持 1：結果只多了兩個選用的鍵、且只在有區間時才出現，舊版 Pi 讀新版 GPU 的結果不受影響 | `JobRequest` 沒有 `extra="forbid"`：舊的 GPU 對不認得的 `range_start` 會默默忽略、處理整支影片。必須在送出之前就知道它做不到 |
| 37 | **成品回報實際處理的區間。** `diarization` 多 `range_start`、`range_end`（秒，一位小數；夾過的實際值；沒有區間時**兩個鍵都不出現**，所以沒有區間的成品與契約 v1 的範例 `speaker_contract_v1.json` 逐位元組相同）。`source_note` 多一句「只處理影片的 mm:ss–mm:ss」，排在說話者區分的警告前面（`mm:ss` 與逐字稿的時間同一種寫法，分鐘不封頂）。Pi 的 `check_speaker_result` 核對：請求有區間 → 結果必須有，起點與請求相差不超過 1 秒、終點不超過請求的終點加 1 秒；請求沒有區間 → 結果不能有；兩個鍵要一起出現 | 讀的人要看得出這篇只涵蓋影片的一段；Pi 要能發現「GPU 沒照做」（舊版、或 GPU 的錯誤）而不是照單全收 |
| 38 | **Pi 記得送出時的區間（遷移 `0016`）。** `Article.range_start`、`Article.range_end`（可為 NULL 的整數秒）。規則照 `speaker_count`：登記或重送之前寫進資料列；接回 GPU 上還在跑（或已跑完）的工作時，區間必須和送出時的一樣，不同就拒絕並說明（等它完成再 `--rerun`）；`--rerun` 失敗而且沒有在 GPU 上留下新工作，還原成目前發佈的那一版的區間；`--dry-run` 印出這次的區間與「之前是」。既有的影片列兩欄都是 NULL（整支）。整個修改是可逆的 | 「再執行同一個指令就會接回去」是這個指令最重要的行為之一；沒有記著，接回一個區間不同的工作，就會發佈另一段內容。先前以為不必動資料庫，是低估了這個行為 |
| 39 | **頁數預設與長度上限看區間。** `slide_range`（預設頁數）與 `--max-minutes` 用**區間的長度**算；`Article.duration_seconds` 仍然是整支影片的長度（那是影片本身的資料）。`end` 超過影片長度時，長度用影片的 | 辯論本體 50 分鐘就該得到 50 分鐘的頁數，而不是整支三小時影片的；長度上限擋的是「要處理的音訊太長」 |
| 40 | **`--rerun` 才能改區間。** 已發佈的影片再給 `--start/--end` 而沒有 `--rerun`，印出「這支影片目前處理的是…；要改區間加 `--rerun`」，不動任何東西（和 `--speakers` 一樣）。`--rerun` 之後說話者編號可能重排、名字不保留（設計文件 #22），換區間也一樣 | 換區間等於換一篇文章的內容，要有明確的動作 |

## 流程（GPU，有區間時）

下載音訊 → **切出區間** → 聲音區分（只吃切出來的檔）→ 語音辨識（只吃切出來的檔）→ **每個區段與每個字的時間加回起點** → 對齊 → 分段 → 摘要 → 核對 → 出片（片段與截圖依原影片的時間抓）。沒有區間時，和以前完全相同。

## 驗證與測試

- GPU：假零件的單元測試（時間加回、指紋、各種錯誤區間、單人拒絕、取消與清理）；API 的測試（請求驗證、`/capabilities`、`runner` 的參數、成品的區間鍵）；真的 ffmpeg 對一段合成 WAV 切出來的長度與內容；沒有區間時的成品與 golden 逐位元組相同。
- Pi：`add_video` 的參數與每一條既有分支（新影片、已發佈、處理中、失敗、`--rerun`、`--dry-run`）；`gpu_client` 的請求鍵與能力檢查；`check_speaker_result` 的區間核對；遷移 `0016`；`label_video` 的連結維持原影片的時間。
- **沒有驗證過的**（需要真的機器）：Docker 映像裡的真 ffmpeg 與真的 pyannote／Whisper／CUDA 吃切出來的檔；LLM 階段與發佈在真的辯論影片上的結果；區間邊界處語音辨識與聲音區分的品質。

## 已知限制

- 區間的邊界可能切在一句話中間：邊界上的第一句與最後一句可能不完整，聲音區分在邊界附近也比較不準。邊界落在停頓或換人的地方最好。
- 聲音區分只看到區間內的聲音：`--speakers N` 的 N 是**區間內**的人數；區間外出現過的人不算。
- 說話者標籤只在同一支影片的同一個區間裡有意義（換區間重做，編號可能全變）。
- 一支影片只有一個區間；要兩段不同的內容，請用兩次（`--rerun` 會覆蓋，所以其實一次只能有一段）。
