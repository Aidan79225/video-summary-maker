# 人物側寫：提案與質詢一致率 — 實作設計

日期：2026-10-03　依據：issue #24 第 5 項（立法產出）裡的「提案與質詢一致率」。第 4、5 步（PR #28）先沒做，因為要用議題分類器替**議案名稱**分領域，而分類器只在質詢摘要上評估過。這裡補上：議案名稱另有自己的人工標註集與門檻，兩道門檻都過才計算。

## 定義

「提的案跟問的事是不是同一個方向」：比較同一會期裡，他**主提案**的領域分布與他**質詢**的主領域分布（第 2 步的分布，只算單獨發言、有摘要卡、通過版本分類的）。

- 提案的領域分布：他主提案、已分類（通過版本）的委員提案，各領域件數 ÷ 件數。
- 一致率 ＝ Σ 各領域 min(提案占比, 質詢占比) × 100（%）。也就是兩個分布重疊的部分：完全一樣是 100%，完全沒有交集是 0%。方法頁用一個小例子說明。
- n ＝ 已分類的主提案件數；套最小樣本（5 件）；另外質詢的基礎文章也要至少 5 篇，不夠就不給值（`reason="few_speeches"`）。百分位的同儕：該會期兩邊樣本都夠的立委（至少 5 人）。
- 不是好壞：方法頁寫明，提案跟質詢方向不同可能是分工，不代表言行不一。

## 議案分類

- 沿用 GPU 的 `topic` 工作與 `topics.TOPICS` 的 12 個領域，送的文字是「議案名稱：<議案名稱>」。不送案由（清單裡沒有，要逐件查）。
- `BillTopic`：bill（一對一）、primary、secondary、classifier、labeled_at。
- 每晚：分類 → 追問 → **議案分類**（`classify_bill_topics`，上限 `BILL_TOPIC_DAILY_LIMIT` 預設 200，新的會期先）→ 重算。失敗處理同 `classify_topics`（GPU 不可用整輪停、開頭連續三件被拒就停、送出後名稱變了不存）。
- 只分「有立委是主提案人」的委員提案。

## 標註與門檻

- `BillTopicLabel`：bill、primary（空字串＝還沒標）、note、labeled_at。`sample_bill_topic_labels [--count 20] [--seed 0]` 從已同步的委員提案隨機抽。
- admin「議案議題標註」：清單上顯示議案名稱與議事網連結，主領域下拉選單直接改；不顯示模型的分類（盲標）。
- `eval_bill_topics`：重新分類已標註的議案，準確率 ≥ 80% 而且至少 20 件才通過，存 `BillTopicEvaluation`（classifier、labeled、correct、accuracy、passed、mistakes、ran_at）。上線規則同議題分布：每個分類器只看自己最新的評估。
- 一致率要**兩道門檻都過**：立法院的議題分類（質詢摘要）與議案分類。兩個分類器的名字可以不同。

## 指標、API、證據

- 院內紀錄區塊的提案組多一張卡 `proposal_alignment`「提案與質詢一致率」（%）。兩道門檻沒過時這張卡不出現。
- 證據：`/records/{id}?session=&kind=proposed` 的每件議案旁標出它的領域（議案分類通過時），卡片說明裡寫「提案 N 件、質詢 M 篇」。卡片的 `evidence_url` 指到 `kind=proposed`。
- `ProfileStat.classifier` 記「議案分類器｜質詢分類器」，API 只在兩個都等於現在上線的版本時給這張卡。

## 方法頁

`#profile-chamber` 補一小節：定義與重疊公式、例子、兩道門檻、為什麼只送議案名稱、限制（名稱很短、委員常一次提一系列同領域的案、不是好壞）。「還沒做的指標」拿掉這一項。

## 測試

- 重疊公式（含兩個例子與邊界）、最小樣本、few_speeches、同儕與百分位、兩道門檻的各種組合、版本不符不算。
- 議案分類：輸入文字、失敗處理、重產（議案名稱變了）、抽樣、盲標、評估。
- API 卡片與紀錄清單的領域標記；網站 check、build、假資料模式。
