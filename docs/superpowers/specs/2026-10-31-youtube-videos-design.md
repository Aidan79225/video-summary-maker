# YouTube 手動加入 — 設計

日期：2026-10-31　狀態：第一部分（來源、指令、網站）已定案，隨這個 PR 交付；第二部分（影片裡不只一個人講話）另外設計，隨下一個 PR 交付，這份文件只在文末留一個位置。使用者授權「其他你決定怎麼做」，決策由本文記錄，可回頭推翻。

## 目標

使用者進 Pi 的容器，用一個 Django 指令貼上手打的 YouTube 網址；影片走跟其他文章同一條 GPU 摘要管線，
做完之後在 news.aidan.tw 的專屬頁面「影片」看到（逐段截圖、重點、完整敘述、可展開的逐字稿，並連回原影片）。

```bash
sudo docker exec ly-news-api python manage.py add_video 'https://www.youtube.com/watch?v=jNQXAC9IVRw' --speakers 1
```

（`--speakers 1`：這個版本只處理一個人講話的影片，沒有它指令會拒絕；多人影片隨下一個 PR 交付，見「指令介面」與文末。）

做完之後：

- 新增一個來源 `youtube`，與立法院、臺中市議會、新北市議會並列，但**不當成議會**：
  人物側寫、議題分類、追問、會期、人物名單都不碰它。
- 首頁與各篩選器維持原樣（只有議會來源）；影片只出現在 `/videos` 與頁首的「影片」連結。
- 每個動作都有對應的指令：加入、重跑、下架。

## 非目標

- 不做每日自動發現（沒有「頻道訂閱」）：每一支影片都是使用者親手挑的。
- 不支援直播中、尚未首播、Shorts、播放清單、頻道頁（理由見下）。
- 不做網站上的輸入框：寫入只走 Pi 上的指令，網站是唯讀的。
- 不改 GPU 管線的既有行為（多人影片要改它，那是下一個 PR 的事，見文末）。

## 探勘結論（皆實測，2026-10-31；Pi 的對外 IP 與開發機不同，第一次在 Pi 上跑要再確認）

| 項目 | 結果 |
|---|---|
| GPU 收什麼網址 | `POST /jobs` 收任何 http(s) 網址，沒有主機白名單；所有 YouTube 形狀都走 yt-dlp 預設分支 |
| GPU 回什麼 | `title`、`source_note`、`transcript_text`、`slides[]`、`brief`；**沒有頻道、上傳日期、長度** |
| oEmbed | `youtube.com/oembed?url=…&format=json` 回 `title`、`author_name`、`author_url`、縮圖；壞 id 回 400，格式正確但不存在回 404；watch、`youtu.be?t=`、shorts、live 形狀都可 |
| 影片頁 | 0.86～1.48 MB、0.2～0.9 秒；瀏覽器與 urllib 的 UA 拿到同樣資料；**影片不存在也回 200**，所以一定要看 `playabilityStatus` |
| 日期 | 影片頁的日期帶太平洋時區；台北時間白天上傳的影片會差一天（動物園那支：太平洋 2005-04-23、台北 2005-04-24） |
| 預設頁數 | GPU 的預設 8～15 頁；19 秒的影片只產出 3 頁，會因「少於下限」失敗 |
| 字幕 | 國昌直播（`f4r2yWk4LV0`，約 95 分鐘、剛結束的直播）只有一條**英文**自動字幕：字幕路徑會選到英文辨識或它的機器翻譯 |
| 容器的 yt-dlp | **尚未驗證**：容器沒有 JS 執行環境、PO token 提供者；需要在 GPU 主機跑一次煙霧測試（見部署） |

## 決策

| # | 決定 | 理由 |
|---|---|---|
| 1 | 來源代碼 `youtube`，顯示名「YouTube」；`Article.ivod_id` 寫成 `yt-<11 碼 id>`，slug 為 `<日期>-yt-<id>`，`ivod_url` **一律存正規網址** `https://www.youtube.com/watch?v=<id>` | 同一支影片用 `youtu.be`、`&t=30s`、`shorts/` 貼，都是同一篇；GPU 的檢查點以網址為鍵，正規化後重試才能接續 |
| 2 | 在 `models.py` 加 `COUNCIL_SOURCES`（立法院、臺中、新北）白名單；`topics.base_articles()`／`followups.is_base()`、四個遍歷 `ArticleSource` 的迴圈、`parse_session`、`profiles` 的 `unsessioned` 查詢、API 預設範圍都用它 | 不用「排除 youtube」的黑名單：下次再加一個非議會來源時不會又漏掉；`Membership`、`Session`、`TopicEvaluation` 的 `choices` 也只列議會來源，管理頁不會出現「YouTube」的任期 |
| 3 | 遷移 `0014`：只有 `choices` 變動（SQL 上是 no-op）；同一個遷移加 `Article.speakers`（JSON，預設空，給下一個 PR 的多人影片用） | 現在一起加最便宜 |
| 4 | API：`SourceParam` 由列舉產生；`/articles`、`/speakers`、`/parties` 省略 `source` 時**只回議會來源**，`?source=youtube` 才回影片；影片清單依 `published_at` 新到舊（新加的影片排最前面，不被它的上傳日期埋到最後幾頁）；`/health` 的 `articles` 算所有已完成的文章（含影片），`latest_date` **只算議會來源** | 首頁、發言者下拉選單、議員頁一行都不用改；`latest_date` 是監控夜間匯入有沒有停擺的訊號，手動加的影片（包括 `--date` 打錯的未來日期）不能影響它 |
| 5 | **影片不進每晚排程**：`process_pending`、`retry_imageless`、`rerun_ready` 都只處理議會來源，影片只由 `add_video` 明確處理 | 一支兩小時的影片會佔住夜間批次並在 GPU 離線時燒掉重試次數；GPU 是使用者的桌機，不該在沒人看的時候自己開一個長工作 |
| 6 | 影片資料在 **Pi 端用標準函式庫**取得（oEmbed → 影片頁 JSON → 使用者覆寫），不引進 yt-dlp | Pi 的相依刻意最少；標題與頻道用 oEmbed，日期、長度、播放狀態從影片頁的 `ytInitialPlayerResponse`（再退到 microdata、正規表示式） |
| 7 | `date` ＝直播開始（或上傳）時刻的**台北時間日期**；抓不到就用今天（台北）並大聲警告（影片頁沒讀到本來就會被預檢拒絕，見 #9，所以只有加了 `--allow-unverified`、或讀得到的播放器回應裡沒有日期時才會走到這一步）；`--date` 可覆寫 | 不用太平洋的日期（差一天） |
| 8 | `speaker` ＝頻道名稱（把「、」換成「・」，因為「、」是聯合質詢的分隔字元）；`meeting` **留空** | 非空的 `meeting` 可能被 `parse_session` 解析成 `Session(source='youtube')`；`--speaker` 讓同一個頻道維持同一個名字 |
| 9 | 預檢（寫進資料庫之前）：影片不存在／不可播、直播中或尚未首播、Shorts → 拒絕並說明；**不公開**（unlisted）、**音樂**類別、超過 `--max-minutes`（預設 180）→ 拒絕，各有明確的覆寫旗標；剛結束的直播（YouTube 還在轉檔）→ 警告，要 `--force`。**檢查不了也是拒絕**（預設）：影片頁沒讀到，或讀到了卻沒解出播放器回應（`playabilityStatus`）→ 不公開、直播中、Shorts、音樂與長度全都檢查不了；解出來了、影片也能播，卻缺了 `isUnlisted`／`isShortsEligible`（真實的頁面，能播放的每一頁都有）→ 缺的那一項檢查不了，訊息點名是哪個欄位。檢查不了是「沒檢查」，不是「沒問題」：要明確加 `--allow-unverified`，放行時警告照舊；`--title`／`--speaker`／`--date` 不能代替它 | 沒有救的影片不會佔一個重試次數；不公開連結被貼到公開網站、整首歌詞被當成逐字稿，都是會後悔的事。oEmbed 連不公開的影片也回標題，所以讀得到標題不代表檢查過了；已經知道的壞消息永遠比「檢查不了」先說。真實頁面本來就可能沒有的欄位（類別、日期、長度…）不算：頂多是警告，不拒絕 |
| 10 | 頁數範圍依長度算：`min = clamp(⌈分鐘/6⌉, 3, 8)`、`max = clamp(⌈分鐘/2⌉, 6, 50)`，`--min-slides`／`--max-slides` 可覆寫 | 預設值讓短影片失敗；上限避免一小時的影片只有十頁 |
| 11 | 語音辨識提示 ＝`f"{speaker}。{title}"[:200]`，由存在資料庫的欄位組成，每次重試一樣 | 提示一變，已存的逐字稿就失效、要重新辨識 |
| 12 | 處理完成後**保留登記時的標題**（使用者用 `--title` 蓋掉時不會被 GPU 的標題換回去），除非它還是佔位的「YouTube 影片 <id>」 | |
| 13 | 重跑語意：`add_video` 遇到已存在的列要說清楚結果——READY：「已發佈在 /article/…」（`--rerun` 才重做，重做時影片留在站上）；FAILED 或次數用完：人為重跑就重設次數；PROCESSING 且有 `gpu_job_id`：先問 GPU 工作的狀態，DONE／RUNNING 就接回去，不等到「卡住」的時間；真的有別人在跑：說還要幾分鐘才會被視為卡住 | 管理頁的「重新排隊」會把 `gpu_job_id` 清掉，幾十分鐘的成品就丟了 |
| 14 | 等待時間用 `settings.GPU_JOB_TIMEOUT_SECONDS`，**不開放更長的 `--timeout`**；長影片要在兩個容器都調大那個環境變數 | 夜間批次用同一個數字判斷「卡住」，指令等得比它久，夜間會把還在跑的工作取消掉 |
| 15 | 下架：`remove_video <網址或 slug>` 刪文章並刪 `MEDIA_ROOT/articles/<ivod_id>/` 的截圖，`--dry-run` 先看。**GPU 工作進行中預設拒絕**（`gpu_job_id` 有值、`updated_at` 還在 2 × `GPU_JOB_TIMEOUT_SECONDS` 之內，不管狀態——`--rerun` 的影片一直是已完成），並說還要幾分鐘；`add_video` 在 `--rerun` 與接回舊工作之前先把 `updated_at` 更新成現在，守衛才看得見這兩條路。**`--force`** 跳過這個守衛（緊急下架不能等上一個小時）並印出警告：GPU 上的工作不會被取消，做完的結果會被丟棄。萬一影片在處理途中還是被下架，`save_result` 對 YouTube 影片在寫入之前確認那一列還在，不在就丟 `ArticleDeleted`：結果丟掉、`add_video` 以非零結束並說「處理途中被下架」，不會讓同一個 pk 又被建立回來 | 管理頁刪文章不會刪檔案，截圖網址仍然可用（Cloudflare 邊緣快取一天，急的話要手動清）；現在刪一支處理中的影片，GPU 做的工作白費，更糟的是做完會把它寫回網站 |
| 16 | 網站：`youtube` 在 `lib/sources.ts` 多一個 `kind: 'video'`；頁首、報頭小字與首頁的來源篩選改用 `COUNCIL_SOURCES`；新增 `/videos` 與頁首的「影片」連結；標籤、「觀看原片」、提示文字都改成 YouTube 的用語；影片頁與文章頁加 `noindex`；不顯示空的「會議」與 0 秒的長度；標題不套 `displayTitle`（會把開頭的日期吃掉）；逐字稿時間戳接受三位數分鐘（`100:05`）；長標題與長頻道名稱可以在任何位置換行（`overflow-wrap:anywhere`：文章標題、卡片、講者頁標題、講者晶片、「看其他影片」連結），375 px 寬的手機不會出現橫向捲軸；`/speaker/<名稱>` 從原始請求路徑取名稱、只解碼一次 | 不加的話影片會被標成「立法院」、「觀看立法院 IVOD 原片」；公開網站上的第三方影片不該被搜尋引擎收錄；沒有空白可以斷行的標題（例如整串網址）原本會把文章頁撐寬到 1400 px；Astro 的 `params` 已經重複解碼過，頻道叫「50%25off」會被解成「50%off」，而它又不還原 `%2F %3F %23 %26 %2B`，所以不能直接用 |
| 17 | 影片的文章頁固定顯示來源註記：「由 AI 依影片自動整理，可能有誤，以原影片為準」＋連回 YouTube，並附逐段的時間連結（`&t=<秒>s`）；摘要卡只有一句話與關鍵數字，**沒有「要求與回應」**（`BriefCard` 對影片來源跳過那一塊） | 與既有的「由語音辨識產生」同一套誠實標示；「未定期限」「未明確回應」是網站替議會質詢發明的標示，套在別人的影片上就成了網站自己編的結論 |
| 18 | **預設就是多人影片**（使用者要求）：不加旗標＝送 GPU 的多人模式；`--speakers 1` 才跳過區分；GPU 做不到就明確失敗，不退回單人寫法。多人模式隨下一個 PR 交付，在那之前一律要 `--speakers 1`（見「指令介面」的過渡一條） | 影片裡不只一個人講話時，正確區分說話的人是這個功能最重要的品質；單人管線把全部的話安給同一個「講者」，多人影片一定寫錯 |

## 指令介面

```text
add_video <網址> [<網址> …]
    --title / --speaker / --date YYYY-MM-DD     只在一個網址時可用，覆寫抓到的資料
    --dry-run                                    只做預檢並印出會登記的資料，不寫資料庫、不呼叫 GPU
    --rerun                                      重做已發佈的影片（影片留在站上）
    --force                                      允許剛結束、YouTube 還在轉檔的直播
    --allow-unlisted / --allow-music             覆寫對應的預檢
    --allow-unverified                           影片頁讀不到、或缺了檢查要用的資料時照樣處理（那些檢查由你負責）
    --max-minutes N                              長度上限，預設 180
    --min-slides N / --max-slides N              覆寫頁數範圍
    --speakers N                                 提示影片有幾個人講話；1＝只有一個人，跳過區分發言者

remove_video <網址、slug 或 yt-id> [--dry-run] [--force]
    --force                                      GPU 工作還在進行中也下架（緊急用）：工作不會被取消，做完的結果會被丟棄
```

- **預設就是多人影片**（使用者的決定，2026-10-31）：沒有任何旗標時，`add_video` 把影片當成可能有好幾個人在講話，送去 GPU 的「多人模式」——用聲音區分說話的人，寫稿時每句話都安到正確的人頭上（做法隨下一個 PR 設計）。`--speakers 1` 才是例外：使用者聲明只有一個人講話，跳過區分，沿用現有的單人管線（寫成「講者」）；`--speakers N`（N≥2）告訴區分的程式要找幾個人。
- **GPU 做不到就明確失敗，不退回單人寫法**：指令送出前先問 GPU 支不支援多人模式；不支援（還沒更新，或說話人區分的模型沒裝好）就停下來說明原因，不寫進資料庫、不佔重試次數。多人模式的結果沒有帶發言者資料時，文章不發佈。
- **過渡（只在這個分支的第一版）**：GPU 端的多人模式在下一個 PR 才做；在它完成之前，沒有 `--speakers 1` 的 `add_video` 一律停下來說明、不送出。這道檢查在那個 PR 換成上一條的「GPU 是否支援多人模式」，那時不加任何旗標就是多人影片。

- **檢查不了也是拒絕**（`--allow-unverified`，見決策 #9）：影片頁沒讀到（被擋下、同意頁、429、逾時）、讀到了卻沒解出播放器回應，或解出來了、影片也能播，卻缺了 `isUnlisted`／`isShortsEligible`，不公開、直播、Shorts、音樂與長度就檢查不了；預設拒絕，不寫進資料庫，訊息說明原因（缺欄位時點名是哪一個）。oEmbed 連不公開的影片也回標題，所以讀得到標題不代表檢查過了。`--title`／`--speaker`／`--date` 只是讓登記不需要影片頁，**不能代替** `--allow-unverified`：oEmbed 與影片頁都讀不到時，要三個覆寫**再加** `--allow-unverified`。放行時照樣印警告，說跳過了什麼。
- **下架**（決策 #15）：GPU 工作進行中預設拒絕並說還要幾分鐘；`--force` 跳過守衛、印警告，工作做完的結果之後會被丟棄，影片不會回來。
- 第一行永遠先印出解析出的 id 與正規網址（網址沒加引號時，bash 會在 `&` 截斷；id 還在，但要讓人看得出來）。
- 接受的形狀：`watch?v=`（帶任何其他參數）、`youtu.be/`、`shorts/`、`live/`、`embed/`、舊的 `/v/`、`/e/`、無協定的寫法、單獨的 11 碼 id。拒絕並說明：只有清單的網址、頻道頁（`/@…`、`/channel/…`；頻道的 `/live` 每次指向不同影片，請貼影片自己的網址）、搜尋、`/clip/`（裡面沒有影片 id）、`v=` 不是剛好 11 碼。
- 不寫死網站網域：完成時印 `/article/<slug>` 與 `/videos`。
- 長影片建議背景執行，斷線不影響：`sudo docker exec -d ly-news-api sh -c "python manage.py add_video 'URL' >> /data/add-video.log 2>&1"`；之後再跑一次同樣的指令會接回已完成的 GPU 工作。

## 網站

`/videos`：沿用首頁的版型（報頭、卡片格線、分頁），沒有篩選器與頭條大卡，一次一個 API 呼叫（`source=youtube`）。
空的時候說「還沒有加入任何影片」，並寫出指令：這個版本寫的是 `add_video '<影片網址>' --speakers 1`（沒有 `--speakers 1` 的指令現在會被拒絕；多人影片交付時拿掉它）。頁首的連結在所有寬度都顯示。

影片的文章頁沒有「要求與回應」（決策 #17）；長標題與長頻道名稱會換行，在 375 px 寬的手機上不會橫向捲動（決策 #16）；`/speaker/<名稱>` 從原始請求路徑取名稱、只解碼一次，所以頻道叫「50%25off」或「Q&A? #1 + more」也找得到自己的影片。

## 風險與限制

- **容器裡的 yt-dlp 沒驗證過**（見部署）。
- **第三方內容**：公開網站上放別人影片的截圖與完整逐字稿，跟政府公開影片不同。這版加 `noindex`、固定標示來源並連回原影片，並提供 `remove_video`；要不要公開、放多少，是使用者的決定。
- **不公開影片與音樂**預設拒絕；頻道改名後新舊影片會變成兩個「發言者」（用 `--speaker` 維持同一個名字）。
- 直式影片的截圖會被 16:9 的框切掉，所以這版不收 Shorts。
- **預設拒絕（fail closed）**：預檢要看的資料讀不到或缺了，就當成沒檢查、拒絕，不是當成沒問題（決策 #9）；能放行的只有操作者明確加 `--allow-unverified`。這條規則只管「檢查本身依賴、真實頁面每一頁都有」的欄位（`playabilityStatus`、`isUnlisted`、`isShortsEligible`）；類別、日期、長度這類本來就可能沒有的欄位缺了只是警告。
- **別人的網站會變**：影片頁與 oEmbed 全用標準函式庫解析，每一層（播放器回應、head 的 microdata、正規表示式）各自攔下預期中的例外（型別不對、數字太大、巢狀太深…）、整層作廢、記成問題、換下一層，所以壞掉的欄位是「讀取時遇到的問題」裡的一行，不是整個指令（連同一次給的其他網址）的 traceback；每次讀取除了逾時另有整體期限（影片頁 30 秒、oEmbed 15 秒），本文比 `Content-Length` 短算連線中斷。
- **上傳者寫的文字不可信**：標題與頻道名稱先清掉控制字元與雙向覆寫字元（ESC、NUL、換行、U+202A–202E、U+2066–2069、零寬空格、孤立的代理字元…）才印、才存；ZWNJ 與 ZWJ 留著，表情符號的組合與波斯文、印地文需要它們，而且它們不會移動游標或讓文字重排。
- **影片裡不只一個人講話時，現有的單人管線會把話安到錯的人頭上**（整條管線都假設只有一個講者）。所以預設就是多人影片（決策 #18），下一個 PR 的多人影片是這個功能的核心，不是選配。

## 測試

- 純函式：網址解析（每種形狀、每種拒絕）、影片頁與 oEmbed 的解析（存下來的真實頁面縮減後當固定資料）、日期換算、頁數範圍、預檢。
- 指令：打過補丁的 `GpuApiClient`、`call_command`；重跑的每個分支；`remove_video` 不留檔案。
- 回歸：`base_articles()` 不含影片；預設的 `/api/articles`、`/api/speakers`、`/api/parties` 不含影片；`?source=youtube` 回影片；`makemigrations --check` 乾淨；夜間處理不碰影片。
- 預檢的「檢查不了」：被擋下的頁面（429、同意頁、機器人檢查）、播放器回應不見、microformat 或旗標被改名，每一種都要拒絕並說出怎麼蓋過，放行時警告照舊；固定資料釘住「真實頁面每一頁都有兩個旗標」；已經知道的壞消息先於「檢查不了」。
- 下架與處理的競態：`remove_video` 在 GPU 工作進行中被拒絕、`--force` 跳過守衛並警告；影片在處理途中被下架時結果被丟棄，不留 traceback、不重建。
- 上傳者的文字：控制字元與雙向覆寫拿乾淨，ZWNJ／ZWJ 留著；畸形的影片頁與 oEmbed 不丟例外。
- 網站：`npm run check`、`npm run build`、`USE_FIXTURE=1` 渲染 `/videos`、影片文章頁（沒有「要求與回應」）與講者頁（路由解碼）。

## 部署

整個 stack 一起重新部署（遷移在容器啟動時跑），完成（api healthy、web 重建）之後才跑 `add_video`；Pi 的兩個映像之間沒有先後。這個版本一律用 `--speakers 1`（單人），不需要更新 GPU 主機；預設的多人模式隨下一個 PR 交付，到時需要**先更新 GPU 主機**（說話人區分的套件與模型）。在 GPU 主機第一次真的處理 YouTube 之前，要做一次煙霧測試，確認容器裡的 yt-dlp 抓得到 YouTube（先短的 `jNQXAC9IVRw`，再長的 `f4r2yWk4LV0`）：失敗時 `add_video` 會把錯誤原樣顯示。

## 第二部分：影片裡不只一個人講話

多人影片的設計（原則、流程、契約、驗證）隨下一個 PR 交付，不寫在這個 PR 的文件裡。在它完成之前，`add_video` 一律要加 `--speakers 1`：決策 #18 與上面「指令介面」裡的「過渡」一條已經寫明，這個版本只處理一個人講話的影片。
